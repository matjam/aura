Why I still write C for old Macs

March 3, 2001 · 7 min read retroc

Every few months someone asks why I bother. The machine on my desk has a 400 MHz processor, 256 MB of memory and an operating system that has not been updated in twenty years. And yet it is the most pleasant computer I own to program for, because it forces every decision into the open.

There is no garbage collector to hide allocation from you, no threads to paper over a slow loop, and no gigabytes of headroom. When something is slow you can usually point to the line that does it.

A small example

Here is the inner loop of a text measurer, simplified. It walks UTF-8 bytes, looks each code point up in a cache and adds the advance:

/* Width of a run of text in 26.6 fixed point. */
static int32_t measure(const Font *f, const char *s, size_t n)
{
    int32_t w = 0;
    for (size_t i = 0; i < n;) {
        uint32_t cp = utf8_next(s, n, &i);
        Glyph *g = cache_get(f->cache, cp);
        if (!g)
            g = cache_fill(f, cp); /* rasterizes on a miss */
        w += g->advance;
    }
    return w;
}

The interesting part is not the loop, it is what is not there: no allocation, no locking, and a single branch on the common path. On a G3 this runs at roughly 40 cycles per character with a warm cache.

Constraints are a gift. They tell you which problems you do not get to have.

What it teaches

  • Measure before guessing: the profiler on a slow machine is brutally honest.
  • Prefer flat arrays to pointer-chasing structures; caches are tiny.
  • Keep recursion shallow. The default stack is 32 KB, and a deeply nested document will find its end.
  • Write the boring version first. It is usually fast enough.

None of this is new, of course. But it is easy to forget on a machine where everything is fast enough until suddenly it is not. A very long word like supercalifragilisticexpialidocious_function_name_that_does_not_fit should overflow or wrap gracefully depending on the style.
